BF16 prefill activations against the wide ones, paired capability comparison.

Recorded on the archived perf/prefill-resid-pool lineage through 4d6d15f8 and
retained here as historical evidence. The current integration did not rerun
this GPU experiment.

Eight generation prompts, 48 tokens each, two-node pipe (layers 0:21 and
21:42), the same binary with INK_ACT_BF16=0 and INK_ACT_BF16=1. INK_POOL_CLEANUP=1
on both arms, which changes no arithmetic.

The BF16 reference row was MISSING when this was written, and said so rather
than leaving a gap that read like a pass: `inkling_bf16_stream.py` wants torch,
and neither box had it installed. It does now, and the row is filled in at the
bottom of this file. What the body of it is instead is the comparison that does
not need it — both arms teacher-forced on the SAME ids as
one uncached forward, so the only thing that differs between the two columns is
the activation dtype, on the same lane, at the same positions. The runtime's own
cached-versus-uncached number is beside it as the floor, exactly as in
attn_bf16_2node.txt, and it is the same floor: whatever our two lanes cost each
other is a floor under anything a dtype can be blamed for.

That 27% is what free generation always looks like once anything differs at all:
after the first flip the two continuations are conditioned on different text and
the comparison stops being about the model. The number worth reading is the
first-divergence column, which is median token 5 against the median token 8 the
BF16 KV cache was accepted at, and the teacher-forced table below.

The first line is OUR two lanes on one arm and has nothing to do with dtype: the
cached decode and the uncached forward disagree 21 times in 384 all by
themselves. It is the same 94.5% the BF16 KV cache measured for the same pair.

The third line is the change. The two dtypes, on the same lane, on the same
input, agree 362 times in 384 -- which is INSIDE the floor the first line sets.
The activation dtype moves this model no further than the runtime's own two
lanes already move it, and no comparison built out of these two lanes can
resolve anything smaller.

=== the missing row, filled in later ===

torch was installed on the box that holds the BF16 checkpoint and the reference
stream was run over these same eight sequences -- 42 layers, 514.5 s, 487.1 GiB
read, one pass for all eight because a stream is per forward and not per prompt.
Scored against the same teacher-forced logs as the table above:

  BF16 reference vs the wide arm    361/384 = 94.0%  [95% CI 91.2-96.0]
  BF16 reference vs the narrow arm  362/384 = 94.3%  [95% CI 91.5-96.2]

  floor: the wide arm's own uncached forward against its own cached
  generation                        363/384 = 94.5%  [95% CI 91.8-96.4]

So the answer to the question this file could not ask is: neither arm is closer
to the unquantised model than the other, and both are as far from it as our own
two lanes are from each other. 361 against 362 of 384 is one position, which
orders nothing.

That is the outcome this file predicted it could not rule out, and it is the
one that makes the narrow arm's acceptance sound rather than merely unfalsified.
See `resid_bf16_2node.txt`, which scores a third arm against the same reference.

=== what this does not say ===

Eight sequences and 384 positions will not detect a small regression, and the
three intervals above overlap almost completely, so "indistinguishable" here
means "not distinguished by 384 positions" and not "equal". The BF16 reference
row closes the originally missing comparison for this set; it does not turn a
small, overlapping sample into a claim about every prompt or sequence length.
